# 新規DBへのゼロからの再現手順（適用順序台帳）

**2026-08-04更新: 田島様のご決定（案C）により、018は
`supabase/migrations_archive/`へ移設済み。** 実行対象の
`supabase/migrations/`ディレクトリには、現在018が存在しない。
したがって新規DBへの適用は「全ファイルを番号順に、一切の除外・修正
なしで適用する」だけでよく、以下に記す旧手順（スキップ運用）は
過去の記録として残すのみで、現在の適用作業には不要である。

## 現在の適用手順

`supabase/migrations/`配下の`*.sql`を、ファイル名の昇順でそのまま
最後まで適用する。除外するファイルはない（001〜017、019〜052。
018は存在しない番号として欠番になる）。

```
001, 002, ..., 017, 019, 020, ..., 051, 052
```

2026-08-04、001→052の完全な連続適用を、018が存在しないディレクトリに
対して実機で確認済み（証跡: `evidence/Stage8_true_hands_off_replay.md`）。

## 018を欠番とした経緯（履歴）

018は2026-07-28に本番へ適用され、当時のポリシー名の衝突がなかった
ため本番では成功した。しかし新規DBへ001から順に適用する場合、
018の`CREATE POLICY snapshot_own_agency ...`が、001が最初から作成
済みの同名ポリシーと衝突し（Postgresエラー42710）、必ず失敗する
ことが2026-08-02の実機検証で判明した。018が本来やろうとしていた
内容は、033（snapshot/candidateのポリシー是正）と023
（`get_my_agency_id()`のis_active対応）が独立して完結する形で
代替しており、018を実行しないことによる新規DB最終状態への影響は
ないことを実機で確認済みだった。

この時点で3つの選択肢（A: ファイルは残し新規DB適用時のみ除外する運用、
B: 018自体を冪等に書き換える、C: 履歴専用ディレクトリへ移す）を
整理して田島様にご判断を仰いだ。田島様は案C（履歴専用ディレクトリへの
移設）を採用するとご決定された。理由は、正規のmigration集合を
「全件を番号順に適用すればよい」という単純な状態に保ち、将来の
自動適用（CI等）で除外運用を忘れることによる事故を防ぐため。

018の内容そのものは、本番の適用履歴（台帳にも登録済み）を保持する
目的で、書き換えずに`supabase/migrations_archive/`へそのまま
移設した。本番環境に対しては、018は既に成功して適用済みであるため、
この移設による変更は不要である。
