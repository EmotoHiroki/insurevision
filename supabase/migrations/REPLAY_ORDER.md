# 新規DBへのゼロからの再現手順（適用順序台帳）

このファイルは、`supabase/migrations/`配下のファイルを**ファイル番号どおりに
適用すると1箇所で失敗する**という、2026-08-01に田島様からご指摘いただいた
問題への対応として作成した。

## 背景（訂正版・2026-08-02実機検証済み）

当初、本ファイルの旧版では「033を018の直後に差し込めば解決する」と
記載していたが、これは誤りだった。実際に新規DB（0テーブルの状態）へ
001→017まで適用したあと018単体を実行して検証したところ、**018は
どこに配置しても単体では成功しない**ことが判明した。

理由: 018の`CREATE POLICY snapshot_own_agency ...`は、事前に
`DROP POLICY IF EXISTS "snapshot_own_agency"`を行わない。ところが
migration 001が最初から同名のポリシー（`snapshot_own_agency`・
`candidate_own_agency`、旧仕様のUSING句）を作成済みのため、018のこの
CREATE POLICY文がPostgresエラー42710（"policy already exists"）で
必ず失敗する。018はこの1文が入った1つのトランザクションであるため、
失敗すると同一migration内の他の変更（`get_my_agency_id()`への
is_active条件追加を含む）もすべてロールバックされ、**018は新規DBに
対して何も反映できない**。

つまり「033を018の直後に手動挿入する」という従来の運用は、実際には
「018を諦めて033に飛ばす」ことと同義だった。033はもともと
`DROP POLICY IF EXISTS`を先に行ってから作成し直す内容になっており、
018が本来やろうとしていたsnapshot/candidateのポリシー是正を、独立して
完結する形で実施できる。また、018のもう一つの変更内容
（`get_my_agency_id()`へのis_active条件追加）も、後続の023
（`023_b1_ms1_get_my_agency_id_search_path.sql`）が関数定義を
まるごと`CREATE OR REPLACE`で書き直しており、018の成否に依存せず
最終的に正しい状態になることを確認済み。019〜022の内容も018の
成否に依存する記述がないことを確認済み。

**結論**: 018を並べ替える必要はない。**018だけを適用対象から除外**すれば、
残り43ファイルは番号どおりの順序でそのまま最後まで適用できる。

## 適用順序（新規DBの場合はこの順序を使うこと）

**ファイル番号どおり、001から044まで昇順で適用する。ただし018のみ
スキップする。** 033を含む他のすべてのファイルは、元の番号の位置で
そのまま適用する（並べ替えは一切不要）。

```
001, 002, ..., 017, [018はスキップ], 019, 020, ..., 032,
033, 034, ..., 044
```

018は「1で作成した`snapshot_own_agency`・`candidate_own_agency`
ポリシーへの追加のis_active/WITH CHECK対応」を意図していたが、
新規DBではこの内容全体が033によって完全に代替される（033は001由来・
018由来どちらのポリシー名も明示的にDROPしてから作り直す設計のため）。
018のもう一方の変更（`get_my_agency_id()`のis_active対応）も023が
独立して完結させる。**018を実行しない**ことによる新規DBの最終状態への
影響はない（2026-08-02、001→044を018スキップで通し適用し、本番との
最終状態一致を実測で確認済み。証跡: `evidence/Stage8_true_hands_off_replay.md`）。

**重要**: 本番DBでは018は実際に成功して適用されている（本番の当時の
ポリシー名が001の名前と衝突しなかったため）。033・023はいずれも
「018が既に成功している状態」に対しても安全に冪等適用できるよう
設計されている。したがって、本番に対しては何も変更する必要がない。
影響を受けるのは「新規DBからゼロで組み立てる場合の適用手順」のみ。

## なぜ018だけなのか

全SECURITY DEFINERの「reproducibility」系migration（008・011〜013・
016・033〜035）を再点検した結果、018以外はすべて以下のいずれかで、
ファイル番号どおりの順序でスキップなしに適用できる:

- 冪等（`IF NOT EXISTS`・`DROP POLICY IF EXISTS`等）で、後から実行しても
  エラーにならない（008・011・012・013）。
- 新規追加のみで、既存オブジェクトとの名前衝突が起きない（016・034・035）。

018だけが、自分自身の`CREATE POLICY`文の前に`DROP POLICY IF EXISTS`を
欠いており、かつ001が同名ポリシーを既に作成済みであるため、新規DBでは
単体で必ず失敗する唯一のケースである。

## この運用について田島様のご承認をお願いしたい点

上記は「001から最新まで番号順に適用する」という原則からの逸脱を1件
含みます。田島様のご依頼は「空の新規DBへ001から最新まで通常順で適用し、
途中介入なしで完走」でしたので、**018を除外するという例外を運用として
正式に採用してよいか**、ご判断をお願いいたします。

考えられる選択肢は次の3つです。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A（現状の提案） | 018はファイルとして残し、新規DB適用時のみ本書の手順で除外する | 本番の適用履歴（018は実際に本番へ適用され台帳にも記録済み）をそのまま保持できる | 「番号順に全ファイルを適用」という単純な運用ではなくなり、本書を読まずに自動適用すると失敗する |
| B | 018のファイル自体を冪等な内容（`DROP POLICY IF EXISTS`を追加）へ修正する | 001から最新まで例外なく順に適用できる | 本番へ適用済みのmigrationファイルを事後に書き換えることになり、「適用済みmigrationは書き換えない」という本案件のこれまでの方針と矛盾する |
| C | 018を`supabase/migrations_archive/`等の履歴専用ディレクトリへ移す | 正規のmigration集合が「全件を番号順に適用すればよい」状態になり、将来の自動適用でも事故が起きない | ディレクトリ構成の変更を伴う。本番台帳との対応関係を別途記録する必要がある |

将来的な自動適用（CI等）での事故を避ける観点では C が最も安全ですが、
本案件のこれまでの方針（適用済みファイルは書き換えない・履歴を保持する）
との整合を優先すると A になります。田島様のご意向をお聞かせください。
