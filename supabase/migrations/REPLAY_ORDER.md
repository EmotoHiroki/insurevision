# 新規DBへのゼロからの再現手順（適用順序台帳）

**2026-08-04更新**: 田島様のご決定（案C）により、018は
`supabase/migrations_archive/`へ移設済み。実行対象の
`supabase/migrations/`ディレクトリには、現在018が存在しない。
したがって新規DBへの適用は「全ファイルを番号順に、一切の除外・修正
なしで適用する」だけでよく、以下に記す旧手順（スキップ運用）は
過去の記録として残すのみで、現在の適用作業には不要である。

## 現在の適用手順

`supabase/migrations/`配下の`*.sql`を、ファイル名の昇順でそのまま
最後まで適用する。除外するファイルはない（018は存在しない番号として
欠番になる）。本書が適用結果まで実機で確認済みの範囲は001〜063
（001〜017・019〜063の62ファイル）である。これより新しい番号の
ファイルがディレクトリに存在する場合は、それらも同じ規則で
番号順に適用する。

```
001, 002, ..., 017, 019, 020, ..., 062, 063
```

> **権限を含む再現性について（2026-08-06更新・解消済み）**: 従来、`anon`・`authenticated`
> へのテーブル権限（GRANT）はいずれのmigrationにも明示されておらず、Supabaseが
> プロジェクト作成時に設定する既定権限に依存していた。そのため`DROP SCHEMA public CASCADE`
> を経た再適用では権限が復元されず、migration一式だけでは本番と同一の状態を
> 再現できなかった。
>
> 田島様2026-08-06ご指摘3を受け、**migration 059でテーブル権限を明示化した**。
> `anon`・`authenticated`から全権限を剥奪したうえで、必要な権限のみを許可リストとして
> 付与する方式である（本番の現在値の機械的コピーではない）。
> これにより、**本手順はスキーマ構成に加えて権限まで再現する**。
> 実際に、下記の通し適用検証では補助的なGRANTを一切与えずに実施し、
> 適用後の権限が本番と完全に一致することを確認している。

**検証状況その1（2026-08-06・001〜060のゼロからの通し適用）**:

2026-08-06、`DROP SCHEMA public CASCADE`で完全にゼロへ戻した検証用DBに対し、
**001〜060の全59ファイルを1スクリプト・人手の介入なしで適用し、エラー0件で完了**
することを実機確認済み（プロジェクト`uwwrtrzhyjormwfyvmrg`）。

適用後の状態が本番と一致することを確認した。

| 項目 | 本番 | 通し適用後の検証DB |
|---|---|---|
| テーブル | 18 | 18 |
| 関数 | 25 | 25 |
| RLSポリシー | 19 | 19 |
| トリガー（public） | 9 | 9 |
| `storage.objects`の証跡保護トリガー | 1 | 1 |

さらに、**名称の一致にとどまらず、定義そのものが一致すること**を確認した。
田島様2026-08-06ご指摘8を受け、列（型・NOT NULL・既定値）・制約・関数本文・
RLSポリシー式・トリガー定義・GRANT を正規化して比較する
`supabase/verification/schema_fingerprint.sql` を新設し、両DBで実行した結果、
**全431オブジェクトについて差分0件・合計MD5が完全一致**（`b721a9adf3ddf94f6…`）
であることを確認している。

この比較により、名称のみの照合では検出できなかった差分が実際に6件見つかり、
migration 060 および該当関数の再適用で解消した（経緯は完了報告書§0第11回改訂を参照）。

**あわせて、migrationだけで構築したDBに対する実HTTP検証を16項目すべて成功で確認した。**
（`supabase/verification/runtime_http_checks.sh`）
手作業での権限付与・スキーマ修正は一切行っていない。スキーマと権限が再現される
だけでなく、再現された環境が実際に動作することを示す証跡である。

なお`DROP SCHEMA public CASCADE`は`public`スキーマへの`GRANT USAGE`も削除するが、
**migration 059がこれを明示的に付与するため、補助的な手当ては不要である。**
上記の検証も、スキーマ再作成の直後に一切のGRANTを与えずに実施している。

**検証状況その2（2026-08-06・061〜062の追加適用）**:

061・062は、上記「その1」の通し適用検証を終えたあとに追加したmigrationである。
本番（`ytpaklotlgrbslshjggc`）と、その1で構築した検証用DB
（`uwwrtrzhyjormwfyvmrg`）の双方へ適用し、いずれもエラー0件で完了した。
どちらのmigrationも末尾に自己検査（`DO $$ ... $$`）を持っており、
期待した状態になっていない場合はその場で例外となって適用が失敗する。

適用後、両DBの状態を再度突き合わせた結果は次のとおりである。

| 項目 | 本番 | 通し適用後の検証DB |
|---|---|---|
| テーブル | 18 | 18 |
| 関数 | 25 | 25 |
| RLSポリシー | 19 | 19 |
| トリガー（public） | 9 | 9 |
| `anon`・`authenticated`へのテーブル権限 | 28 | 28 |
| 001が定義するベースラインインデックス | 7 | 7 |

定義そのものの比較も再実施した。列（型・NOT NULL・既定値、232件）・制約（92件）・
関数本文（25件）・RLSの有効/強制状態（18件）・RLSポリシー式（22件）・
トリガー定義（14件）・テーブル権限（28件）・インデックス定義（46件）の
**8分類・合計477オブジェクトについて差分0件**である。
関数のEXECUTE権限についても、`anon`・`authenticated`を対象とする21件が
両DBで完全に一致している（連結MD5 `1e516a9436d67982…`）。

「その1」の431オブジェクトとの関係: 431はその1で列挙した7分類
（列・制約・関数本文・RLS有効状態・RLSポリシー式・トリガー定義・テーブル権限）の
合計である。本節の477は、その7分類にインデックス定義46件を加えたものであり、
431を含む上位集合である（431 + 46 = 477）。件数が異なるのは比較の対象範囲を
広げたためで、その1の結果と矛盾するものではない。

意図的に一致させていない差分が2点ある。いずれも本番側にのみ存在するもので、
検証DB側は本番より権限が絞られた（安全な側の）状態である。

| 差分 | 内容 | 扱い |
|---|---|---|
| `service_role`への関数EXECUTE権限 | 本番にはSupabaseがプロジェクト作成時に設定する既定権限が残っており、`public`配下に作成した関数が自動的に`service_role`へ開放される。検証DBにはこの既定権限が無い | 既定権限をmigrationで再現すると、以後`public`に作成する全オブジェクトが自動的に開放されることになり、059で確立した「明示的に許可したものだけを許可する」方式と正面から矛盾する。したがって意図的に再現しない。`service_role`はサーバー側でのみ用いる鍵であり、`anon`・`authenticated`の到達範囲には影響しない |
| `run-pdfs`バケット | 本番にのみ存在し、どのmigrationも作成していない。オブジェクト0件、ソース全体からの参照も0件で、Phase2-b以前の残置と考えられる | 削除は本番の実体を消す操作にあたるため、本手順およびmigrationでは扱わない。取り扱いは別途ご判断を仰ぐ |

**検証状況その3（2026-08-06・001〜063のゼロからの通し適用。現在値の正）**:

「その2」は061・062を既存の検証DBへ追加適用した記録であり、
ゼロからの通し適用ではなかった。063の追加にあわせて、
`DROP SCHEMA public CASCADE`で完全にゼロへ戻した検証用DBに対し、
**001〜063の全62ファイルを1スクリプト・人手の介入なしで適用し、
エラー0件で完了**することを改めて実機確認した（プロジェクト`uwwrtrzhyjormwfyvmrg`）。
補助的なGRANTやスキーマ修正は一切行っていない。

適用後の状態と本番を、定義レベルで突き合わせた結果は次のとおりである。

| 比較対象 | 件数 | 差分 |
|---|---|---|
| 列（型・NOT NULL・既定値） | 232 | 0 |
| 制約 | 92 | 0 |
| 関数本文・SECURITY DEFINER・search_path | 25 | 0 |
| RLSの有効/強制状態 | 18 | 0 |
| RLSポリシー式 | 22 | 0 |
| トリガー定義 | 14 | 0 |
| `anon`・`authenticated`へのテーブル権限 | 28 | 0 |
| インデックス定義 | 46 | 0 |
| **合計（8分類）** | **477** | **0** |

関数のEXECUTE権限についても、`anon`・`authenticated`を対象とする
25関数×2ロール＝50件の比較で差分0件である。

「その2」の時点で残っていたインデックス7件の差分は、migration 062の適用により解消した。
現時点で意図的に一致させていない差分は、上表の直前に記した2点
（`service_role`への既定権限、`run-pdfs`バケット）のみである。

さらに、migrationだけで構築したこのDBに対して、
**同梱の検証SQL14ファイルが全件成功し、実HTTP検証も24項目すべて成功**することを確認した。
（`supabase/verification/run_all_checks.sh` および `runtime_http_checks.sh`）
スキーマ・権限が再現されるだけでなく、再現された環境が実際に想定どおり
動作し、かつ想定どおり拒否することを示す証跡である。

## 018を欠番とした経緯（履歴）

018は2026-07-28に本番へ適用され、当時のポリシー名の衝突がなかった
ため本番では成功した。しかし新規DBへ001から順に適用する場合、
018の`CREATE POLICY snapshot_own_agency ...`が、001が最初から作成
済みの同名ポリシーと衝突し（Postgresエラー42710）、必ず失敗する
ことが2026-08-02の実機検証で判明した。018が本来やろうとしていた
内容は、033（snapshot/candidateのポリシー是正）と023
（`get_my_agency_id()`のis_active対応）が独立して完結する形で
代替しており、018を実行しないことによる新規DB最終状態への影響は
ないことを実機で確認済みだった。

この時点で3つの選択肢（A: ファイルは残し新規DB適用時のみ除外する運用、
B: 018自体を冪等に書き換える、C: 履歴専用ディレクトリへ移す）を
整理して田島様にご判断を仰いだ。田島様は案C（履歴専用ディレクトリへの
移設）を採用するとご決定された。理由は、正規のmigration集合を
「全件を番号順に適用すればよい」という単純な状態に保ち、将来の
自動適用（CI等）で除外運用を忘れることによる事故を防ぐため。

018の内容そのものは、本番の適用履歴（台帳にも登録済み）を保持する
目的で、書き換えずに`supabase/migrations_archive/`へそのまま
移設した。本番環境に対しては、018は既に成功して適用済みであるため、
この移設による変更は不要である。
