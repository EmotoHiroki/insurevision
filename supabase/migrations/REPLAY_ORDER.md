# 新規DBへのゼロからの再現手順（適用順序台帳）

**2026-08-04更新**: 田島様のご決定（案C）により、018は
`supabase/migrations_archive/`へ移設済み。実行対象の
`supabase/migrations/`ディレクトリには、現在018が存在しない。
したがって新規DBへの適用は「全ファイルを番号順に、一切の除外・修正
なしで適用する」だけでよく、以下に記す旧手順（スキップ運用）は
過去の記録として残すのみで、現在の適用作業には不要である。

## 現在の適用手順

`supabase/migrations/`配下の`*.sql`を、ファイル名の昇順でそのまま
最後まで適用する。除外するファイルはない（001〜017、019〜060。
018は存在しない番号として欠番になる）。

```
001, 002, ..., 017, 019, 020, ..., 059, 060
```

> **権限を含む再現性について（2026-08-06更新・解消済み）**: 従来、`anon`・`authenticated`
> へのテーブル権限（GRANT）はいずれのmigrationにも明示されておらず、Supabaseが
> プロジェクト作成時に設定する既定権限に依存していた。そのため`DROP SCHEMA public CASCADE`
> を経た再適用では権限が復元されず、migration一式だけでは本番と同一の状態を
> 再現できなかった。
>
> 田島様2026-08-06ご指摘3を受け、**migration 059でテーブル権限を明示化した**。
> `anon`・`authenticated`から全権限を剥奪したうえで、必要な権限のみを許可リストとして
> 付与する方式である（本番の現在値の機械的コピーではない）。
> これにより、**本手順はスキーマ構成に加えて権限まで再現する**。
> 実際に、下記の通し適用検証では補助的なGRANTを一切与えずに実施し、
> 適用後の権限が本番と完全に一致することを確認している。

**検証状況（2026-08-06時点・migration 060まで）**:

2026-08-06、`DROP SCHEMA public CASCADE`で完全にゼロへ戻した検証用DBに対し、
**001〜060の全59ファイルを1スクリプト・人手の介入なしで適用し、エラー0件で完了**
することを実機確認済み（プロジェクト`uwwrtrzhyjormwfyvmrg`）。

適用後の状態が本番と一致することを確認した。

| 項目 | 本番 | 通し適用後の検証DB |
|---|---|---|
| テーブル | 18 | 18 |
| 関数 | 25 | 25 |
| RLSポリシー | 19 | 19 |
| トリガー（public） | 9 | 9 |
| `storage.objects`の証跡保護トリガー | 1 | 1 |

さらに、**名称の一致にとどまらず、定義そのものが一致すること**を確認した。
田島様2026-08-06ご指摘8を受け、列（型・NOT NULL・既定値）・制約・関数本文・
RLSポリシー式・トリガー定義・GRANT を正規化して比較する
`supabase/verification/schema_fingerprint.sql` を新設し、両DBで実行した結果、
**全431オブジェクトについて差分0件・合計MD5が完全一致**（`b721a9adf3ddf94f6…`）
であることを確認している。

この比較により、名称のみの照合では検出できなかった差分が実際に6件見つかり、
migration 060 および該当関数の再適用で解消した（経緯は完了報告書§0第11回改訂を参照）。

**あわせて、migrationだけで構築したDBに対する実HTTP検証を16項目すべて成功で確認した。**
（`supabase/verification/runtime_http_checks.sh`）
手作業での権限付与・スキーマ修正は一切行っていない。スキーマと権限が再現される
だけでなく、再現された環境が実際に動作することを示す証跡である。

なお`DROP SCHEMA public CASCADE`は`public`スキーマへの`GRANT USAGE`も削除するが、
**migration 059がこれを明示的に付与するため、補助的な手当ては不要である。**
上記の検証も、スキーマ再作成の直後に一切のGRANTを与えずに実施している。

## 018を欠番とした経緯（履歴）

018は2026-07-28に本番へ適用され、当時のポリシー名の衝突がなかった
ため本番では成功した。しかし新規DBへ001から順に適用する場合、
018の`CREATE POLICY snapshot_own_agency ...`が、001が最初から作成
済みの同名ポリシーと衝突し（Postgresエラー42710）、必ず失敗する
ことが2026-08-02の実機検証で判明した。018が本来やろうとしていた
内容は、033（snapshot/candidateのポリシー是正）と023
（`get_my_agency_id()`のis_active対応）が独立して完結する形で
代替しており、018を実行しないことによる新規DB最終状態への影響は
ないことを実機で確認済みだった。

この時点で3つの選択肢（A: ファイルは残し新規DB適用時のみ除外する運用、
B: 018自体を冪等に書き換える、C: 履歴専用ディレクトリへ移す）を
整理して田島様にご判断を仰いだ。田島様は案C（履歴専用ディレクトリへの
移設）を採用するとご決定された。理由は、正規のmigration集合を
「全件を番号順に適用すればよい」という単純な状態に保ち、将来の
自動適用（CI等）で除外運用を忘れることによる事故を防ぐため。

018の内容そのものは、本番の適用履歴（台帳にも登録済み）を保持する
目的で、書き換えずに`supabase/migrations_archive/`へそのまま
移設した。本番環境に対しては、018は既に成功して適用済みであるため、
この移設による変更は不要である。
